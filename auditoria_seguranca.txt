# 🔒 Auditoria de Segurança — Plataforma Fênix v1.0.4

**Data:** 16/09/2026  
**Escopo:** Análise estática de código (sem testes de penetração ativos)

---

## Resumo Executivo

A aplicação demonstra **maturidade de segurança acima da média** para o porte do projeto: JWT com httpOnly/Secure/SameSite, refresh token rotation com detecção de reuso, separação por subdomínio, RLS no Supabase, validação de magic bytes em uploads, rate limiting por IP em múltiplas camadas, CSP em produção. Existem, porém, **vulnerabilidades críticas** (chaves expostas) e pontos que precisam atenção antes de um deploy em produção real.

---

## 🔴 CRÍTICO — Exige Ação Imediata

### 1. Chaves e Segredos Expostos no `.env` (SUPABASE_SERVICE_ROLE_KEY)

**Arquivo:** [`.env`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/.env)

| Segredo | Risco |
|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` (L5) | **Acesso TOTAL ao banco** — ignora RLS, pode ler/escrever/deletar qualquer dado, criar/excluir contas |
| `JWT_SECRET` (L13) | Permite **forjar qualquer JWT** de admin/user/support |
| `VIMEO_ACCESS_TOKEN` (L16) | Acesso à conta Vimeo (leitura, possível exclusão de vídeos) |
| `VIMEO_CLIENT_SECRET` (L18) | Par de OAuth completo — pode gerar tokens |
| `NIPPONFLEX_SENHA_MD5` (L26) | Acesso à API de cadastro de D.I.s |

> [!CAUTION]
> O `.env` está no `.gitignore` e **nunca foi commitado** (confirmado pelo `git log`). Porém a pasta inteira (`Plataforma Fenix v1.0.4`) está no Desktop — **qualquer software com acesso ao disco (malware, backup em nuvem, screenshot, compartilhamento de tela) pode ler esses segredos**. Se este `.env` for o de produção, todas as chaves devem ser rotacionadas.

**Recomendação:**
- Rotacionar imediatamente `SUPABASE_SERVICE_ROLE_KEY`, `JWT_SECRET`, `VIMEO_CLIENT_SECRET` e `NIPPONFLEX_SENHA_MD5`
- Usar um gerenciador de segredos (Vault, Doppler, variáveis de ambiente do host de produção)
- Nunca manter `.env` de produção na mesma máquina de desenvolvimento

### 2. `SUPABASE_URL` e `SUPABASE_ANON_KEY` Injetados no Bundle do Frontend

**Arquivo:** [`vite.config.ts:19-20`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/vite.config.ts#L19-L20)

```ts
'process.env.SUPABASE_URL': JSON.stringify(process.env.SUPABASE_URL || ''),
'process.env.SUPABASE_ANON_KEY': JSON.stringify(process.env.SUPABASE_ANON_KEY || ''),
```

Embora a `anon_key` seja projetada para ser pública (é um JWT com role `anon`), aqui ela revela:

- **O IP do Supabase self-hosted** (`169.58.193.43`) — permite ataques diretos ao PostgreSQL/GoTrue (port scanning, brute-force)
- O frontend pode tentar conexões diretas ao Supabase — se o RLS estiver mal configurado, o anon pode ler dados sensíveis

> [!IMPORTANT]
> Validar se estas variáveis são de fato usadas no frontend. Se não forem, **remover do `define`** para não expor o IP do servidor no bundle JavaScript público.

### 3. Supabase Self-Hosted em IP Público Sem TLS

**Arquivo:** [`.env:3`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/.env#L3)

```
SUPABASE_URL="http://169.58.193.43"
```

- Protocolo `http://` (sem TLS): **todas as chamadas do servidor ao banco trafegam em texto puro** — passwords, tokens de sessão, dados pessoais de D.I.s, conversas de suporte
- Em rede compartilhada ou cloud, um atacante com acesso ao segmento de rede (sniffing) pode capturar a `SERVICE_ROLE_KEY` em trânsito
- O IP direto (sem domínio) impede o uso de certificados TLS válidos

**Recomendação:**
- Configurar TLS (HTTPS) no Supabase self-hosted
- Usar um domínio com certificado Let's Encrypt
- Restringir acesso por firewall ao IP do servidor da aplicação

## 🟠 ALTO — Vulnerabilidades Relevantes

### 4. Like e Comment Sem Autenticação

**Arquivo:** [`server.ts:2160`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/server.ts#L2160) e [`server.ts:2175`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/server.ts#L2175)

```ts
app.post("/api/fenix-social/posts/:id/like", fenixSocialInteractionRateLimiter, async (req: any, res) => {
app.post("/api/fenix-social/posts/:id/comment", fenixSocialInteractionRateLimiter, async (req: any, res) => {
```

Essas rotas **NÃO usam `authenticateUser`**. Qualquer visitante anônimo pode:
- Curtir posts infinitamente (o `userKey` cai para `req.ip` ou `"anonymous"`)
- Postar comentários com nome arbitrário (`usuarioNome` do body é spoofável)
- O `fenixSocialInteractionRateLimiter` (30/5min por IP) ajuda mas não impede abuso via múltiplos IPs

**Impacto:** Spam de comentários, inflação de likes, impersonação de nomes

### 5. Nipponflex: TLS Desabilitado (`rejectUnauthorized: false`)

**Arquivo:** [`nipponflexService.ts:32`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/src/server/nipponflexService.ts#L32)

```ts
const nipponflexAgent = new https.Agent({ rejectUnauthorized: false });
```

Permite ataques Man-in-the-Middle à API da Nipponflex. Um atacante na mesma rede pode interceptar credenciais (`NIPPONFLEX_CODIGO`, `NIPPONFLEX_SENHA_MD5`) e dados de cadastro de 2.684 D.I.s (nomes, códigos, situações).

**Recomendação:** Obter o certificado raiz da cadeia da Nipponflex e adicioná-lo como CA trusted:
```ts
const nipponflexAgent = new https.Agent({ ca: fs.readFileSync('nipponflex-ca.pem') });
```

### 6. Sessões Persistidas em Disco Sem Proteção de Acesso

**Arquivo:** [`server.ts:312`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/server.ts#L312), [`server.ts:452`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/server.ts#L452)

| Arquivo | Contém |
|---|---|
| `data/refresh_sessions.json` (25KB) | Tokens de refresh (text), supabaseToken criptografado |
| `data/jti_sessions.json` (9KB) | JTI → code (D.I.) mapeamentos, supabaseToken criptografado |
| `data/.dev-jwt-secret` | JWT secret de dev |

**Positivo:** Os `supabaseTokens` são criptografados (AES-256-GCM) derivados do `JWT_SECRET`.

**Negativo:**
- Os arquivos ficam em `data/` — qualquer processo com acesso ao filesystem pode lê-los
- Os `refreshToken` em si estão **em texto puro** nos JSONs — quem ler o arquivo pode assumir qualquer sessão
- `data/` está no `.gitignore` mas não tem permissões restritas no filesystem

**Recomendação:** Criptografar também os refresh tokens at-rest, ou usar um store com acesso restrito (Redis com auth, SQLite criptografado)

### 7. `PUBLIC_BASE_DOMAIN` Não Definido — Host Spoofing

**Arquivo:** [`server.ts:625`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/server.ts#L625), [`.env:20`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/.env#L20)

```
# PUBLIC_BASE_DOMAIN=<dominio raiz do site, ex.: grupofenix.com> — quando definido...
```

Está **comentado**. Sem ele, qualquer host que comece com `adminfenix.` é aceito como admin host:
```ts
if (host.startsWith(ADMIN_HOST_PREFIX)) {
    if (APP_BASE_DOMAIN && !host.endsWith("." + APP_BASE_DOMAIN)) return false;
    return true; // <-- sem APP_BASE_DOMAIN, qualquer sufixo passa
}
```

Um atacante pode apontar `adminfenix.atacante.com` para o IP do servidor e acessar as rotas de admin (ainda precisa de credenciais, mas a superfície de ataque fica exposta).

**Recomendação:** Definir `PUBLIC_BASE_DOMAIN=grupofenix.com` (ou o domínio real) em produção

## 🟡 MÉDIO — Pontos de Atenção

### 8. `ADMIN_PASSWORD` em Texto Puro (Fallback Ativo)

**Arquivo:** [`server.ts:1026-1028`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/server.ts#L1026-L1028)

```ts
if (process.env.ADMIN_PASSWORD) {
    console.warn("[Aviso] Senha admin verificada em texto puro...");
    return safeEqualStr(input, String(process.env.ADMIN_PASSWORD));
}
```

Se `ADMIN_PASSWORD_HASH` não estiver definido mas `ADMIN_PASSWORD` estiver, a senha é comparada em texto puro (via `timingSafeEqual`, ok para timing, mas a senha fica em claro nas variáveis de ambiente). Atualmente o `.env` não define nenhum dos dois (login admin é via Supabase Auth), mas o fallback existe.

### 9. `cookie: secure` Depende de `NODE_ENV`

**Arquivo:** [`server.ts:922`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/server.ts#L922), [`server.ts:1143`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/server.ts#L1143)

```ts
secure: process.env.NODE_ENV === "production",
```

Se em produção `NODE_ENV` não estiver definido como `"production"` (deploy mal configurado), os cookies **não terão flag Secure** e serão enviados em HTTP (interceptáveis).

### 10. Token do Login Retornado no Body da Resposta

**Arquivo:** [`server.ts:1162`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/server.ts#L1162)

```ts
res.json({
    success: true,
    user: publicUser,
    token: accessToken  // <-- access token no body
});
```

O `accessToken` é retornado tanto no cookie httpOnly (seguro) quanto no body da resposta JSON. Isso é feito para fallback quando cookies de terceiros são bloqueados, mas o token fica acessível ao JavaScript do frontend e exposto a ataques XSS (se houver alguma brecha de XSS).

### 12. Sessões In-Memory Sem Teto por Conta

**Arquivo:** [`server.ts:300-308`](file:///c:/Users/johnn/Desktop/Plataforma%20Fenix%20v1.0.4/Plataforma%20Fenix/server.ts#L300-L308)

Os maps `refreshSessions`, `usedRefreshTokens`, `jtiSessions`, `revokedJtis` crescem em memória. Há podas (30d, 10000 itens) para `usedRefreshTokens` e `jtiSessions` (2000 teto), mas `revokedJtis` é um `Set` sem limite — um ataque com muitos logouts pode crescer indefinidamente.

## 📊 Análise de Rate Limiting — O que TEM e o que FALTA

### ✅ Rotas Com Rate Limiting (já implementadas)

| Rota | Limiter | Limite |
|---|---|---|
| `POST /api/auth/login` | `loginRateLimiter` + lockout por conta | 10/15min IP + 10/15min conta |
| `POST /api/ouvidoria/submit` | `ouvidoriaRateLimiter` + custom IP map | 5/10min + 5/15min |
| `POST /api/admin/upload-file` | `uploadRateLimiter` | 20/15min |
| `POST /api/storage/upload` | `uploadRateLimiter` | 20/15min |
| `POST /api/fenix-social/posts` | `fenixSocialPostRateLimiter` | 10/15min |
| `POST .../like`, `POST .../comment` | `fenixSocialInteractionRateLimiter` | 30/5min |
| `GET .../moderacao`, `POST .../aprovar|recusar` | `fenixModeracaoRateLimiter` | 30/15min |
| `POST /api/support/change-password` | `passwordChangeRateLimiter` | 8/15min |
| `POST /api/admin/support-users/:email/reset-password` | `passwordChangeRateLimiter` | 8/15min |
| `GET /api/vimeo/*` | `vimeoInfoRateLimiter` | 60/15min |
| Todas `/api/*` | `globalApiRateLimiter` | 150/min |

### ❌ Rotas Que Precisam de Rate Limiting Adicional

| Rota | Risco | Recomendação |
|---|---|---|
| `GET /api/content/public` | **Scraping/DDoS** — dados públicos (cursos, materiais, banners) em cache de 20s, mas sem rate limit específico. Bot pode esgotar a banda. | Limitar a **30 req/min por IP** (o `globalApiRateLimiter` dá 150/min, muito alto para esta rota pesada) |
| `GET /api/content/restricted` | **Data harvesting** — retorna todos os cursos com módulos e URLs de vídeos | Limitar a **20 req/min por IP** |
| `POST /api/content/download/:id` | **Download flood** — pode gerar alto tráfego de storage | Limitar a **10 downloads/min por IP** |
| `POST /api/fenix-social/posts/:id/like` | **Sem autenticação** — like bombing via IPs rotativos | Exigir `authenticateUser` + reduzir limite para **10/5min** |
| `POST /api/fenix-social/posts/:id/comment` | **Sem autenticação** — spam de comentários anônimos | Exigir `authenticateUser` + reduzir limite para **10/5min** |
| `GET /api/fenix-social/posts` | **Scraping do feed** — cache de 30s mas sem rate limit próprio | Limitar a **30 req/min por IP** |
| `GET /api/storage/preview/*` | **Abuso de preview** — pode cachear mas o fetch ao Storage pode ser excessivo | Limitar a **60 req/min por IP** |
| `GET /api/storage/stream/*` | **Video scraping** — stream ilimitado de vídeos | Limitar a **30 req/min por IP** |
| `GET /api/storage/hls/*` | **HLS segment flooding** — segmentos .ts sem limite | Limitar a **100 req/min por IP** (HLS pede muitos segmentos) |
| `POST /api/admin/backup/create` | **Backup DoS** — backup consome CPU/IO/Storage | Limitar a **2 req/15min** |
| `POST /api/admin/backup/restore` | **Restore DoS** — restauração é pesadíssima | Limitar a **1 req/15min** |
| `POST /api/admin/nipponflex/sync` | **Sync flood** — cada sync consome 5+ min de API externa | Limitar a **1 req/30min** (já tem check `em_andamento`) |
| `POST /api/support/tickets` | **Ticket flood** — criação de chamados sem rate limit | Limitar a **5 tickets/15min por D.I.** |
| `POST /api/support/tickets/:id/messages` | **Spam de mensagens no suporte** | Limitar a **10 msgs/5min por D.I.** |
| `POST /api/support/tickets/:id/anexos` | **Upload flood de anexos** | Já usa `uploadRateLimiter` (ok) |
| `GET /api/manutencao/status` | **Endpoint público, cache de 30s** — ok mas pode ser abusado | Rate limit de **20/min por IP** |
| `GET /api/auth/me` | **Session probing** — verificações rápidas de autenticação | Limitar a **30/min por IP** |
| `GET /api/support/sse` | **SSE connection exhaust** — sem limite de conexões SSE por IP | Limitar a **3 conexões SSE simultâneas por IP** |
